\section{Query \& Retention Policies}
\subsection{Retention Design}
Retention is configured at the bucket level in InfluxDB v2, and the bucket-level setting is the sole retention mechanism. The \texttt{telemetry} bucket's retention is set on first start by \path{DOCKER_INFLUXDB_INIT_RETENTION}; the \texttt{waveform} buckets' retention is set by \texttt{daq2-ingest} when it first creates them.

\begin{table}[H]
  \caption{Retention}
  \begin{center}
    \begin{tabular}{llp{0.45\linewidth}}
      \hline
      \textbf{Bucket} & \textbf{Retention} & \textbf{Rationale}\\
      \hline
      \texttt{telemetry} & 90 days & Covers the thesis validation period \\
      \texttt{waveform} & 7 days (default) & Set by disk capacity (Section~\ref{sec:fullrate}) \\
      \texttt{waveform\_1s} & Indefinite & Long-term trends at small storage cost \\
      \hline
    \end{tabular}
  \end{center}
\end{table}

At the as-built publish rate of one burst per channel every 5~s, storage growth is small, and 90 days of data from two nodes is well within the capacity of the historian host.

\subsection{Downsampling}
\label{sec:downsampling}
The original design specified a Flux scheduled task, \texttt{downsample\_1m}, aggregating the \texttt{telemetry} bucket into an indefinitely retained \texttt{telemetry\_1m} bucket. This was superseded by the full-rate path: \texttt{daq2-ingest} computes per-second RMS, mean, minimum, and maximum values from every sample as it ingests them, and writes them to the indefinitely retained \texttt{waveform\_1s} bucket (Section~\ref{sec:fullrate}). Computing aggregates in the ingestion service avoids a scheduled task re-reading around 21 million raw points per minute, and RMS, rather than the mean used in the original design, is the meaningful long-term quantity for AC waveforms, whose mean over a whole number of cycles is approximately zero.

The \texttt{telemetry} bucket itself is not downsampled; at one burst per channel every 5~s, 90-day retention does not constrain storage.

\subsection{Key Query Patterns}
\label{sec:queries}
The following Flux examples cover the primary query patterns, written against the as-built schema.

A single channel, one row per burst with \texttt{sync}, \texttt{dt\_ns}, and \texttt{v\_0} to \texttt{v\_19} as columns:
\begin{lstlisting}[language=flux]
from(bucket: "telemetry")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "mqtt_consumer"
                    and r.node_id == "node_01"
                    and r.subsystem == "voltage"
                    and r.metric == "phase_a")
  |> pivot(rowKey: ["_time"], columnKey: ["_field"], valueColumn: "_value")
\end{lstlisting}
Data written since the burst-splitting processor was added is also available one point per sample in the \texttt{samples} measurement (filter on \texttt{\_measurement == "samples"} and \texttt{\_field == "v"}). For older data, per-sample timestamps are reconstructed as \texttt{\_time} $+ k \cdot$ \texttt{dt\_ns} for field \texttt{v\_}$k$; the export script \path{grafana_export.py} performs this expansion when exporting to CSV with \texttt{--samples}.

Cross-node comparison for the same channel, using the first sample of each burst:
\begin{lstlisting}[language=flux]
from(bucket: "telemetry")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "mqtt_consumer"
                    and r.subsystem == "voltage"
                    and r.metric == "phase_a"
                    and r._field == "v_0")
  |> group(columns: ["node_id"])
\end{lstlisting}

Cross-node comparisons are only meaningful where both nodes report \texttt{sync} = 1 for the bursts concerned.

All channels from a single node (debugging):
\begin{lstlisting}[language=flux]
from(bucket: "telemetry")
  |> range(start: -15m)
  |> filter(fn: (r) => r.node_id == "node_01")
\end{lstlisting}

PTP lock state over a window:
\begin{lstlisting}[language=flux]
from(bucket: "telemetry")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "mqtt_consumer"
                    and r._field == "sync")
  |> group(columns: ["node_id"])
\end{lstlisting}

\subsection{Grafana Integration}
\label{sec:grafana}
Grafana connects to InfluxDB v2 via the native Flux data source. Both the data source and the dashboard are provisioned from the repository, so a fresh deployment needs no manual configuration:
\begin{itemize}[noitemsep]
  \item The data source (\path{grafana/provisioning/datasources/influxdb.yml}) reads its token from \texttt{INFLUXDB\_TOKEN}, which Docker Compose passes to the Grafana container. Its uid is pinned to the value Grafana originally generated for it, so that existing panels and the export script continue to reference it.
  \item The \textit{DAQboard} dashboard (\path{grafana/provisioning/dashboards/daqboard.json}) is loaded into a \textit{Microgrid} folder. It may be edited in Grafana, but must be exported back to the repository for changes to persist.
\end{itemize}
